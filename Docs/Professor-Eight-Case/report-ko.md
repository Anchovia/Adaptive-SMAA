# 교수님 보고용 ①–⑧ 정리

제목: [연구 진행 보고] TSCMAA 스타일 SMAA 오버헤드 개선 및 8개 구성 비교

교수님, 안녕하세요. 전병훈입니다.

말씀해 주신 “TSCMAA 스타일 구현 오버헤드를 줄이면 알려 달라”는 내용과 관련하여 진행 결과를 정리했습니다.

직전 edge를 유지하는 구현에서 불필요한 비용이 큰 실행 경로를 수정하여, 같은 화면 출력을 유지하면서 전체 AA 시간을 Bistro에서 13.94%, Minecraft에서 4.39% 줄였습니다. 다만 수정된 원본 SMAA T2X-R과 비교하면 Bistro는 9.53% 짧고 Minecraft는 아직 3.33% 길어, 모든 장면에서 원본보다 빨라졌다고 판단할 단계는 아닙니다. 속도 개선과 별개로 얇은 선 단절·이동 중 반짝임도 남아 있습니다.

1. 비교 기준선에서 확인한 스텐실 초기화 누락

사용 중인 Intel CMAA2 데모의 SMAA 연동 코드를 확인한 결과, SMAA 전용 stencil buffer를 매 프레임 초기화하는 처리가 누락되어 있었습니다. 스텐실 기능 자체가 없는 것이 아니라, 이전 프레임의 edge 표시를 지우지 않아 현재 edge가 아닌 위치에서도 공간 처리 셰이더가 불필요하게 실행될 수 있는 상태였습니다.

SMAA 저자의 공식 데모에는 매 프레임 초기화가 있으므로, 이는 SMAA 알고리즘 자체의 결함이 아니라 저희가 사용한 CMAA2 데모의 SMAA 통합 코드에서 확인한 누락입니다. 정상적인 실행 조건을 복원한 것이며 새로운 AA 알고리즘의 성과로 계산하지 않았습니다. 코드 근거는 [CMAA2의 SMAA 연동 코드](https://github.com/GameTechDev/CMAA2/blob/071c6b0857559f4e36f614362e6d2aab1b61938a/Projects/CMAA2/SMAA/vaSMAAWrapperDX11.cpp#L270)와 [SMAA 저자 데모의 초기화 코드](https://github.com/iryoku/smaa/blob/71c806a838bdd7d517df19192a20f0c61b3ca29d/Demo/DX10/Code/Demo.cpp#L601)입니다.

SMAA 1X에서 초기화 유무만 바꾼 독립 비교 결과는 다음과 같습니다. 초기화 비용도 아래 시간에 포함했습니다.

| 장면 | 초기화 누락 상태 (ms) | 초기화 적용 후 (ms) | AA 시간 변화 |
|---|---|---|---|
| Bistro | 0.141096 | 0.093481 | 33.75% 감소 |
| Minecraft | 0.216874 | 0.160594 | 25.95% 감소 |

두 장면 각각 240프레임, 총 480프레임의 RGB는 수정 전후가 완전히 같았습니다. 이후 비교 기준선에도 필요한 stencil 초기화를 반영했고, 이미 초기화하던 선택적 처리에는 중복 호출을 넣지 않았습니다. AA-Off와 전체 화면 Temporal-only에는 사용하지 않는 SMAA stencil 초기화를 추가하지 않았습니다. 아래 성능은 이 수정이 반영된 결과입니다.

2. 현재 비교하는 8개 구현

| 구성 | 공간 AA | Temporal 범위 | 지터/표본 패턴 | 구현 요약 |
|---|---|---|---|---|
| ① AA-Off | 없음 | 없음 | Off | AA 없이 렌더링한 기준군입니다. |
| ② SMAA 1X | 원본 SMAA | 없음 | Off | Edge 검출·혼합 가중치 계산·주변 색상 혼합의 공간 3패스만 수행합니다. |
| ③ Temporal-only | 없음 | 전체 화면 | On | 공간 보정을 생략하고 전체 화면에서 원본 T2X-R 결합을 수행합니다. |
| ④ SMAA + 원본 T2X-R | 원본 SMAA | 전체 화면 | On | 공간 SMAA 뒤 원본 T2X-R을 수행하는 주 비교 기준선입니다. |
| ⑤ Edge temporal-only | 없음 | 현재 edge | Off | 1차 edge 검출은 수행하되 공간 색상 보정은 생략하고, 검출된 edge에서만 temporal 셰이더를 실행합니다. |
| ⑥ SMAA + 현재 edge temporal | 원본 SMAA | 현재 edge | Off | 공간 SMAA를 유지하면서 1차 pass의 정확한 edge 표시를 stencil로 전달하여 해당 픽셀에서만 temporal 셰이더를 실행합니다. |
| ⑦ 직전 edge 유지 — 개선 전 | 원본 SMAA | 현재 + 직전 edge | Off | 직전 raw edge를 두 버퍼로 교대 보관하고 재투영해 현재 edge와 합칩니다. 기존 3차 pass에서 선택 영역을 SV_Depth로 전달합니다. |
| ⑧ 직전 edge 유지 — 개선 후 | 원본 SMAA | ⑦과 같은 영역 | Off | 동일한 선택 영역을 1차 pass의 stencil에 표시해 3차 pass의 shader depth 출력을 제거했습니다. 추가 draw/dispatch 없이 ⑦과 같은 출력을 유지합니다. |

⑤~⑧은 TSCMAA의 선택 처리 아이디어를 원본 SMAA temporal 결합에 적용한 실험입니다. Temporal이 있는 구성은 depth와 카메라 행렬에서 계산한 camera-motion velocity로 재투영합니다. 이 자료는 움직이는 개별 물체의 motion vector까지 검증한 결과는 아닙니다. ③·④는 원본의 paired jitter/subsample pattern On, ⑤~⑧은 Off이므로 차이를 모두 edge 선택만의 효과로 해석하지 않았습니다. 또한 이 8개 번호는 이번 비교용 구성으로, 별도로 계획한 Original/Adaptive 최종 8개 조합과는 구분됩니다.

⑦에서 ⑧로 바꿀 때는 이전 edge 보관이나 temporal 수식을 바꾸지 않았습니다. 추가 edge 저장은 원래부터 두 texture를 교대하는 구조였으며 매 프레임 전체 edge를 복사하지 않았습니다. 비용 분리 실험에서 3차 pass의 SV_Depth 출력 경로가 큰 추가 비용을 보였고, 같은 선택 결과를 1차 pass의 stencil로 전달하도록 수정했습니다. 기존 두 장면의 총 480프레임과 이번에 연장한 두 장면의 총 960프레임에서 ⑦·⑧의 최종 RGB가 완전히 일치했습니다.

3. 전체 AA 시간 및 temporal 시간

RTX 3060 Ti / DX11 Release x64 / SMAA Ultra / 1920×1061 / VSync Off 조건입니다. 성능 측정은 PNG 저장·진단 readback을 끈 독립 프로세스에서 300프레임 준비 후 4,800프레임씩 반복했습니다. ①·②·③·⑤는 기존 6회 반복 결과, ④·⑥·⑦·⑧은 최신 동일 실행의 3회 반복 결과를 사용했습니다.

전체 AA 시간에는 공간 AA, 필요한 준비 작업, camera velocity 생성 및 temporal resolve가 포함됩니다. 음수는 ④보다 시간 감소, 양수는 증가입니다.

중요한 비교 조건으로, 각 행의 변화율은 해당 구성과 같은 실행에서 측정한 수정된 ④를 분모로 계산했습니다. 실행마다 기준선 시간이 조금 달라, 표의 ④ 행 절대값을 다른 모든 행의 공통 분모로 사용하지 않았습니다. 전체 AA 시간의 감소율은 전체 렌더링 FPS 향상률과도 다릅니다. ①의 0 ms는 AA 작업이 없다는 의미입니다.

Temporal 결합 단계만 분리하면 다음과 같습니다. 이 표에는 공간 처리와 camera velocity 생성 비용이 포함되지 않습니다.

현재 edge만 사용하는 ⑥은 ④ 대비 전체 AA 시간이 Bistro 15.06%, Minecraft 4.19% 짧았습니다. 직전 edge까지 유지하는 ⑧은 ⑦보다 빨라졌지만, 여전히 ⑥보다 비용이 큽니다. 공간 AA가 없는 ⑤는 ③보다 전체 AA 시간이 길었습니다. Edge 검출·준비 비용까지 새로 부담하는 구성에서는 결합 단계의 절약만으로 전체 비용이 줄지는 않았습니다. 따라서 “선택적 처리의 실행 비용 감소”는 확인했으나 “더 넓은 영역을 처리하면서 속도와 품질을 모두 개선했다”는 결론은 아직 내리지 않았습니다.

4. 품질 결과와 남은 한계

프레임을 직접 비교하면, ⑥은 이동 중 얇은 선이 끊기거나 일부 프레임에서 사라지는 문제가 있습니다. ⑦·⑧은 Minecraft의 일부 프레임에서 그 선을 이어 주지만, 다른 프레임의 단절과 반짝임까지 해결하지 못했습니다. ⑧은 동일 출력의 비용 최적화이므로 ⑦보다 품질이 좋아진 구현은 아닙니다. 확인한 얇은 선 구간에서는 원본 ④가 더 안정적으로 구조를 유지합니다.

보조 지표인 CGVQM-2 결과도 함께 정리했습니다. 높을수록 좋으며, 이동은 f60~179, 정지 전환은 f160~219입니다.

5. 비교 자료 및 다음 검토 방향

비교 자료는 위쪽 ①·②·③·④, 아래쪽 ⑤·⑥·⑦·⑧ 순서로 배치했습니다. 기존 Minecraft 얇은 선, Bistro 의자·창문에 Bistro 발코니 난간과 Minecraft 나뭇잎을 추가하여 총 5개 확대 구간의 느린/빠른 GIF와 정상 속도 영상을 준비했습니다. 독립 3D 장면은 Bistro와 Minecraft 두 개이며, 위 다섯 개는 관찰 영역입니다.

추가로 두 장면 각각 실제 8초 분량의 새 타임라인을 캡처했습니다. 정지 1초 → 기존 속도로 연속 이동 6초 → 정지 1초이며, 기존 4초 영상을 반복하거나 느리게 늘린 자료가 아닙니다. 정상 속도 영상과 느린/빠른 GIF를 함께 구성했습니다. 자료의 index.html에서 각 비교를 확인하실 수 있습니다.

현재까지는 원본 기준선의 누락을 수정하고 선택적 temporal의 실행 오버헤드를 줄이는 데 진전이 있었습니다. 다음에는 ⑧에 남은 공간 단계 비용과, 속도 개선만으로 해결되지 않은 얇은 선 단절·반짝임을 각각 분리해 검토하겠습니다. 원본 ④의 시각적 안정성과 전체 AA 비용을 함께 만족하는지 확인하며 연구를 진행하겠습니다.

## 재현 및 검증 기록

보고서 브랜치는 `tooling/eight-case-professor-report`, 출발점은 `9e8461a`이다. 렌더러는 변경하지 않았다. 독립 기준선별 캡처 브랜치는 `long-capture-summary.json`에 기록했다. 각 브랜치는 대응 기준선에서 분기하고 캡처 harness만 480프레임으로 연장했다.

성공한 10개 clean process에서 24개 시퀀스, 총 11,520 PNG를 생성·검증했다. 각 모드의 처음 180프레임 RGB는 원래 짧은 캡처와 동일하다. 독립 브랜치의 native ④는 audit ④의 모든 480프레임과 동일하다. ⑦/⑧도 각 장면 480프레임 전체 RGB가 동일하다.

③ Minecraft의 두 실행은 첫 캡처 이전 renderer 준비 단계에서 멈춰 해당 PID만 종료했다. 미완료 결과는 사용하지 않았다. 이후 캡처 진입 전 저장된 AA만 Off로 두고 재시도했으며 실제 mode/warmup/timeline은 그대로 유지했다. 성공한 ③ Minecraft와 ⑤ 두 장면은 이 시작 설정을 사용했다. 원본 구간 및 전체 native control RGB 일치로 캡처 조건을 확인했다.
